# ICE-SC-002 — Session Conditions First Canonical Production Slice

## 1. Purpose

Authorize implementation of the remaining first canonical Session Conditions
production slice established by IC-SC-001 — Session Conditions Implementation
Contract.

ICE-SC-001 remains the completed execution authority for canonical Growing
commencement. Commit `3dfe4b28eec7388dd54c2e357ad1fb2451d3f4b3` records
implementation of that prerequisite. This artifact does not reopen, redefine,
duplicate, replace, or supersede ICE-SC-001.

Execution shall realize approved authority without establishing,
reinterpreting, extending, or replacing architecture.

This artifact authorizes implementation work only. It creates no Foundation
truth, Product Composition, canonical authority, lifecycle authority,
repository-governance authority, or presentation authority.

## 2. Governing Authority

Implementation inherits, in order:

1. Grow Platform Architecture;
2. Grow Architecture Governance;
3. applicable Foundation Notes, including FN-004, FN-005, FN-006, and FN-007;
4. applicable Product Composition Specifications, including CS-SC-001,
   CS-SC-001A, and CS-SC-001B;
5. IC-SC-001, as supplemented without replacement by IC-SC-001B; and
6. ICE-SC-001 solely as the completed execution authority for canonical
   Growing commencement.

Higher-order authority remains governing.

Commit `3dfe4b28eec7388dd54c2e357ad1fb2451d3f4b3` is repository
evidence that the canonical Growing commencement prerequisite has been
implemented. It creates no architectural or execution authority.

Architectural ambiguity, contradiction, or insufficient authority shall stop
execution. Implementation shall not resolve such conditions through
convenience, precedent, inferred behavior, or working code.

## 3. Execution Scope

Execution is limited to the remaining IC-SC-001 first production slice
containing exactly two canonical Session Conditions dimensions:

1. **Grow Method**
2. **Environment Type**

For both dimensions, execution is limited to:

- canonical Session containment;
- reuse of the existing IC-GC-002C vocabularies without expansion;
- period applicability only;
- first applicability beginning exactly at authoritative canonical Growing
  commencement;
- stable condition-period identity;
- inclusive period starts and exclusive period ends;
- initial declaration;
- operational change;
- correction with attributable revision history;
- immutable ownership, authorship, source, and creation provenance;
- deterministic, non-overlapping chronology;
- deterministic historical and Current Conditions retrieval;
- Canonical Platform derivation of Current Conditions;
- canonical-to-Product adapters and read-only Product consumption;
- owner-scoped authorization and access-safe retrieval;
- atomicity, rollback, concurrency protection, stale-write protection,
  idempotency, and duplicate prevention;
- deterministic migration of eligible legacy truth; and
- atomic per-Session authority cutover.

Session-wide applicability, record-level applicability, and additional
dimensions are not authorized.

Canonical Growing commencement is an implemented Session Lifecycle
prerequisite. This execution consumes it through the authoritative lifecycle
boundary and does not create, derive, repair, normalize, correct, replace, or
persist a competing commencement fact.

## 4. Authorized Implementation

Implementation may establish the internal production mechanisms required to
realize the following approved behavior.

### 4.1 Canonical condition periods

For each authorized dimension, implementation may persist correction-aware
condition periods that:

- have one stable, immutable identity;
- belong to exactly one canonical Session;
- identify exactly one authorized dimension;
- contain one canonically normalized approved value and permitted `Other`
  text;
- contain one inclusive start and an optional exclusive end;
- preserve original actor, creation, source, migration, and correction
  provenance;
- preserve deterministic revision and update facts; and
- never overlap another authoritative period for the same Session and
  dimension.

Persistence shall enforce at most one open period and one unique period start
for each Session and dimension. Duplicate canonical periods are prohibited.

Normalization shall reuse the existing IC-GC-002C behavior and approved
vocabularies. No new value, dimension, unrestricted key, or generic condition
model is authorized.

### 4.2 Initial declaration

Initial declaration may establish the first canonical period for one
authorized dimension only when:

- the actor is authenticated and authorized through the parent Session;
- the dimension and value are approved and canonically normalized;
- authoritative Growing commencement exists;
- the first period begins exactly at that commencement;
- no first or overlapping period already exists; and
- identity, provenance, chronology, and operation outcome persist atomically.

Duplicate submission shall return the same canonical result without duplicate
truth. A declaration failure shall leave no partial condition period.

### 4.3 Operational change

Operational change may record a real change in circumstances by atomically:

- validating owner authority, approved value, and canonical chronology;
- closing the current period at the authorized change boundary;
- opening one succeeding period at the same boundary;
- preserving the prior period as historically true;
- rejecting overlap, stale state, conflicting state, or an invalid boundary;
  and
- preserving deterministic history and Current Conditions.

An operational change creates a new stable condition-period identity. It shall
not rewrite the preceding period as though the new circumstance had always
been true.

### 4.4 Correction

Correction may repair inaccurate recorded truth without fabricating an
operational transition.

Implementation may correct only the value and permitted `Other` text, period
start, or period end authorized by IC-SC-001. It must preserve immutable
Session containment, condition-period identity, dimension, original actor,
original creation facts, and prior correction provenance.

Every correction shall:

- retain attributable before-and-after facts, actor, timestamp, operation
  identity, and revision;
- revalidate the complete dimension chronology;
- keep the first applicable period anchored exactly at canonical Growing
  commencement;
- reject overlap, inversion, stale state, conflict, or chronology preceding
  commencement;
- recalculate affected canonical projections; and
- commit correction history and affected canonical state atomically.

### 4.5 Retrieval and projection

The Canonical Platform may provide deterministic, access-safe retrieval of:

- all canonical Session Conditions for one authorized Session;
- conditions applicable at an authorized canonical chronological point;
- historical operational periods;
- attributable correction-aware history; and
- canonical Current Conditions.

Historical ordering shall follow IC-SC-001: applicability start ascending,
Grow Method before Environment Type, then stable condition-period identity.

Current Conditions shall be derived exclusively by the Canonical Platform
from canonical Session truth, authoritative commencement, corrected condition
periods, half-open applicability, the authoritative platform clock, and the
viewer's authorization context.

Retrieval and projection shall preserve the IC-SC-001 distinction among known,
not applicable, absent, unknown, and unresolved canonical meanings. A
transport, service, or retrieval failure shall remain distinguishable from an
unresolved canonical result.

Anonymous reads shall be denied unless existing Session architecture
separately authorizes a read. Correction-history retrieval and protection
shall be equivalent to canonical condition-period protection.

Products may consume, organize, and explain canonical results. Product and
Presentation code shall not independently derive, renormalize, persist,
override, or reconstruct canonical truth.

### 4.6 Migration, cutover, and compatibility

Implementation may migrate one eligible canonical Session only from:

- its authoritative parent Session and owner truth;
- authoritative canonical Growing commencement;
- its authoritative existing Grow Method value and permitted `Other` text;
  and
- its authoritative existing Environment Type value and permitted `Other`
  text.

Each valid legacy dimension may establish one equivalent open canonical period
beginning exactly at authoritative Growing commencement. Migration shall
preserve approved value meaning, permitted `Other` text, Session containment,
and attributable source provenance.

Eligibility requires authoritative source truth and authoritative canonical
Growing commencement. A Session lacking either remains unresolved or
ineligible for chronology-dependent migration. No created, updated,
Germination-completion, decision, evidence, migration, deployment, inferred,
estimated, reconstructed, or administrator-selected time may substitute.
Generic Session creation is not Growing commencement.

Before canonical authority changes for an eligible Session, implementation
shall verify:

- complete source-to-target coverage for every eligible source value;
- approved-value parity for Grow Method;
- approved-value parity for Environment Type;
- canonical Growing commencement for every migrated period;
- canonical projection parity for both dimensions;
- Session ownership and containment;
- no duplicates or overlaps;
- security enforcement;
- deterministic retry behavior;
- no partial migration; and
- no partial transfer of canonical authority.

Migration and authority cutover shall form one atomic per-Session outcome:

- before successful validation and cutover, the Growing Phase fields remain
  the sole canonical authority for that Session;
- consumers shall not switch early;
- successful cutover makes canonical Session Conditions the sole authority for
  both dimensions for that Session;
- legacy write authority retires at cutover;
- failure rolls back target writes or leaves them inaccessible and
  non-authoritative without changing legacy authority; and
- no observable state exposes dual canonical authority or no canonical
  authority.

After a successful cutover, deployment rollback shall not silently reactivate
legacy canonical authority or discard canonical conditions and attributable
history created after cutover.

If a reverse authority transition is supported, it shall preserve all
post-cutover canonical truth and attributable history, satisfy an equivalent
atomic authority-transition gate, and prevent simultaneous, missing, or
ambiguous canonical ownership.

Temporarily retained legacy fields remain non-authoritative compatibility data.
They receive no canonical writes after cutover, cannot override or correct
Session Conditions, cannot supply Current Conditions, and cannot regain
authority through fallback behavior.

If a legacy-shaped response remains temporarily necessary, it shall be derived
read-only from canonical Session Conditions. Indefinite dual writing and
permanent dual authority are prohibited.

Compatibility ends when repository inspection and focused verification prove
that all production Growing and Product Composition consumers read canonical
Session Conditions. At that point, the temporary compatibility adapter shall
be removed. Compatibility shall not persist beyond its authorized transition
purpose.

### 4.7 Operation identity and concurrency

Every canonical declaration, operational change, correction, migration, and
authority transition shall use:

- one stable operation identity;
- deterministic operation input; and
- an expected canonical revision or equivalent stale-write guard.

Repeating an identical completed operation shall return the established
canonical result without duplicate truth. Reusing an operation identity with
different input shall be rejected. A stale expected revision or
chronology-conflicting operation shall be rejected.

Concurrent operations shall resolve deterministically without partial
condition periods, correction history, migration state, projections, or
canonical authority. Fingerprint, revision, and conflict validation shall not
be weakened to make a retry succeed.

Implementation teams retain freedom to choose schema organization,
transaction mechanisms, service or RPC organization, indexes, deployment
sequencing, concurrency controls, query optimization, and internal adapters,
provided every governed outcome remains satisfied.

## 6. Implementation Boundaries

The Canonical Platform exclusively owns Session Conditions truth,
normalization, applicability, chronology, provenance, correction history,
retrieval meaning, and Current Conditions derivation.

Each condition period remains contained by exactly one canonical Session.
Session ownership determines mutation and retrieval authority.

Canonical periods and correction history receive equivalent owner-scoped
protection. Anonymous reads are denied unless existing Session architecture
separately authorizes a read. Canonical history is protected from unauthorized
alteration or erasure, and canonical mutation remains confined to the
authorized operation boundary.

Parent-Session deletion shall leave no orphaned condition period, orphaned
correction history, inaccessible condition truth, or cross-owner data
exposure. The internal deletion mechanism remains an implementation choice.

Session Lifecycle exclusively owns canonical Growing commencement.
ICE-SC-001 and its completed implementation remain unchanged. ICE-SC-002
consumes that prerequisite and gains no lifecycle authority.

Both dimensions use period applicability only. The first period begins at
canonical Growing commencement. Session-wide applicability, record-level
applicability, and direct condition-to-record relationships remain prohibited.

Product adapters transport and organize canonical meaning without creating a
parallel model. Products and Presentation remain read-only with respect to
canonical Session Conditions and Current Conditions.

Implementation may select internal technical mechanisms but may not alter:

- canonical ownership or Session containment;
- the two authorized dimensions or their existing vocabularies;
- period-only applicability or half-open boundary meaning;
- declaration, operational-change, or correction semantics;
- historical durability or provenance;
- deterministic Current Conditions derivation;
- migration eligibility or unresolved legacy meaning;
- the atomic per-Session authority transition;
- owner-scoped security;
- lifecycle, Growing commencement, or Session Context authority; or
- Product and Presentation non-authority.

No user-interface, workflow, navigation, component, layout, styling, Timeline,
Calendar, analytics, reporting, notification, recommendation, automation,
artificial-intelligence, sensor, or presentation behavior is authorized.

- implement a dimension beyond Grow Method and Environment Type;
- add, rename, reorder, merge, or reinterpret approved vocabulary values;
- create an unrestricted condition key or generic key-value model;
- create Session-wide applicability for either dimension;
- create record-level applicability or a direct condition-to-record
  relationship;
- create or change lifecycle authority;
- reopen, redefine, duplicate, repair, or replace canonical Growing
  commencement;
- substitute `created_at`, `updated_at`, Germination completion, a decision
  timestamp, first evidence, generic Session creation, or another capability
  record for commencement;
- fabricate, infer, estimate, approximate, reconstruct, recover, backdate, or
  administratively select chronology;
- migrate or cut over a Session whose required source truth or commencement is
  unresolved;
- perform speculative legacy backfill;
- create a parallel canonical store, duplicate history, or independently
  persisted Current Conditions;
- expose dual canonical ownership, indefinite dual writing, or early consumer
  cutover;
- preserve legacy write authority after successful cutover;
- permit legacy compatibility data to override canonical Session Conditions;
- retain a temporary compatibility adapter after all production consumers
  read canonical Session Conditions;
- create Product-owned or Presentation-owned canonical truth;
- permit Product or Presentation to derive applicability or Current
  Conditions independently;
- independently delete canonical condition periods;
- erase correction history or canonical historical truth;
- use a deletion path that bypasses parent-Session authority;
- mutate canonical truth outside the authorized canonical operations;
- create a privileged browser or service-role write path;
- change Session ownership, privacy, sharing, authorization, or unrelated
  security boundaries;
- implement UI or presentation work;
- implement unrelated Grow Companion work or CS-GC-008;
- perform unrelated refactoring, optimization, cleanup, dependency, asset, or
  documentation work; or
- perform governance or repository-organization work.
