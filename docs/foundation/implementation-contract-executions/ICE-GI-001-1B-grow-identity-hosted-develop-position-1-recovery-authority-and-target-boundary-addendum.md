### 18.1 Overall Diagnosis

Position 1's twelve nonconformities arise from four shared causes:

1. **Evidence-free completion:** schema defaults, triggers, backfill, and
   clients convert missing or ambiguous evidence into asserted `grower`,
   `new`, or `profile_type` meaning.
2. **Authorization applied too late:** raw fields influence public output,
   search matching, ordering, or metadata before field-level authorization.
3. **Duplicated mutation authority:** broad direct table grants and the
   Profile client's upsert bypass the canonical RPC's allowlist,
   protected-field rules, normalization, and provenance.
4. **Cross-domain authority leakage:** generic Identity directly serializes
   Recognition state and treats a Vault share as general Identity access.

The recommended design uses four consolidated correction units. Existing
migrations remain immutable; eventual implementation should use one
forward-only corrective migration plus the minimum consumer and regression
changes. The exact migration timestamp and filename remain later
implementation choices.

### 18.2 Recommended Correction Structure

#### CU-1 — Truthful Evidence and Legacy Quarantine

Covers invariants `6` and `47`.

- Remove schema, trigger, backfill, and live-client defaults that manufacture
  `grower`, `new`, `profile_type`, or equivalent completion.
- Permit missing canonical role and experience values rather than enforcing
  non-null fabricated defaults.
- Classify existing values before any write:
  - supported and attributable: retain;
  - proven migration-generated fallback: convert to absent;
  - invalid: exclude from canonical output;
  - ambiguous or provenance-free: preserve raw evidence but treat it as
    legacy-unresolved and omit it from canonical output;
  - explicitly owner-confirmed: retain with atomic `self_declared`
    provenance.
- A member may confirm or clear a value through the canonical mutation
  boundary.
- Presentation may use a neutral label such as “Grow member” but must not
  persist or return a fabricated role.

Future surfaces:

- One new forward-only corrective migration.
- `src/grow-identity-contract.js`
- Live normalization and Profile-consumer paths in `app.js`
- Focused Identity regression fixtures.

#### CU-2 — Canonical Mutation and Protected-Field Boundary

Covers invariants `18`, `28`, and `31`.

- Retire authenticated browser insert/upsert and broad direct-update authority
  on `public_member_profiles`.
- Route supported Identity edits exclusively through
  `update_my_grow_identity_v1`.
- Preserve RLS as defense in depth, not as a substitute for least-privilege
  grants.
- Remove `profile_type`, `account_type`, owner/user identifiers, verification,
  reserved identity, QR state, timestamps, and provenance from
  owner-controlled payloads.
- Make value and provenance updates atomic.
- Replace the live Profile client's direct table upsert with canonical RPC
  consumption.
- Split any non-Identity Profile setting from Identity mutation. If no
  independently authorized safe Profile operation exists, stop for separate
  Profile authority rather than retaining the broad path.

Future surfaces:

- Forward-only migration grants, triggers, and canonical RPC definitions.
- `app.js` Profile save route.
- Identity contract parity and direct/RPC regression coverage.

#### CU-3 — Deny-Closed Visibility, Public Projection, and Search

Covers invariants `12`, `13`, `17`, and `46`, plus the search/output portion
of `20`.

- Missing field-visibility rows return `false` for every non-owner scope.
- Owner access remains available without turning missing evidence into public
  or connection access.
- Build every non-owner payload from an explicit per-context allowlist.
- Omit raw `username`, protected/system state, profile state, timestamps,
  preferences, provenance, and other non-allowlisted keys.
- Replace the public view with a minimal explicitly public projection; no
  `coalesce(..., 'public')` fallback is permitted.
- Search must match and sort only on values already authorized for that
  viewer. Filtering, ordering, and limiting happen after authorization.
- Update `PUBLIC_MEMBER_PROFILE_SAFE_SELECT` and live client normalization to
  match the reduced safe projection without reintroducing defaults.

Future surfaces:

- `grow_identity_field_visible_v1`
- `get_grow_identity_v1`
- `search_grow_identities_v1`
- `safe_public_member_profiles`
- [Position 2's effective projection definition](../../../supabase/migrations/20260719140000_profile_hero_catalog_safe_projection.sql)
- `app.js` public-profile select and normalization
- Privacy, anonymous, search-side-channel, and compatibility regressions.

#### CU-4 — Recognition, Vault, and Security-Definer Containment

Covers invariants `20`, `34`, and `36`.

- Generic Identity must stop querying and serializing Recognition tables,
  `is_verified`, or Recognition-derived identity labels.
- Because no separately authorized privacy-safe Recognition projection is
  established, the recommended treatment is omission—not invention of a new
  projection.
- Recognition-owned owner functionality and durable Recognition records
  remain unchanged.
- Withdraw the generic public Recognition wrapper from Identity-facing use
  unless a later separately governed Recognition projection is approved.
- Remove Vault-share status as a bypass in `get_grow_identity_v1`; a Vault
  share must not create general Profile or Identity access.
- Preserve existing Vault-specific sharing and purpose-bounded
  owner-attribution RPCs.
- Audit every affected security-definer function for caller, target,
  authorization, output, ownership, fixed search path, and execution grants.

Future surfaces:

- `get_grow_identity_v1`
- `get_public_identity_and_recognition`
- Related grants
- Existing Vault-specific RPCs as preservation boundaries
- Security-access and function-access regression scripts.

### 18.4 Internal Ordering

1. Define the evidence-category decision table without mutation.
2. Correct read, source-domain, and public disclosure boundaries first: CU-3
   and CU-4.
3. Establish the canonical mutation-only boundary: CU-2.
4. Apply truthful default/backfill treatment only after safe mutation and
   classification exist: CU-1.
5. Run the complete local matrix, failure injection, consumer compatibility,
   privilege graph, and function audit.
6. Stop before connected qualification, execution, security fingerprint work,
   or Position 2.

No data treatment may precede classification. No client deployment may
precede server-side privacy and mutation enforcement.

### 18.5 Cross-Cutting Acceptance Criteria

A future implementation is acceptable only when:

- Existing predecessor migrations remain byte-identical.
- Exactly one forward-only correction supplies the database changes.
- Every unsupported or ambiguous value remains absent or noncanonical until
  evidenced or confirmed.
- No missing visibility row broadens disclosure.
- Non-owner and anonymous payloads contain only explicitly allowlisted keys.
- Hidden values have no observable search effect.
- Direct Identity table writes are denied to authenticated browser clients.
- Canonical writes atomically enforce owner, allowlist, normalization,
  protected fields, and provenance.
- Generic Identity contains no direct Recognition or verification output.
- Vault sharing produces no generic Profile access.
- Existing Recognition records, Vault grants, identifiers, owners,
  intentional privacy, and durable references remain unchanged.
- Every affected security-definer function and effective privilege is audited.
- All focused and full local verification is deterministic across clean apply,
  rerun, interruption, and retry.
- Any authority ambiguity stops rather than selecting implementation evidence
  as architecture.
